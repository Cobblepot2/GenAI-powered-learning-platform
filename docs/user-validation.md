# 用户验证计划与空白记录

本文件提供可执行的验证方法。目前没有提供已完成的访谈、受试者反馈或用户验证结果，不能将下面的预期或空白表格写成发现。

## 要验证的假设

1. 学习者能理解课程入口，并独立完成一门短微课。
2. 选择题后的解释能帮助学习者理解原因。
3. 教师能理解“规则模板草稿”的局限，编辑后完成本机发布。
4. 用户能区分本机进度、正式账号与班级参与数据。

建议先邀请至少 2 名不同背景的学习者和 1 名教师开展探索性验证。人数是计划，不是已接触人数。记录采用匿名编号，避免收集姓名、学号等不必要信息；录音或录像前单独征求同意。

## 单次安排（约 15 分钟）

**开场，1 分钟**

“我们正在验证一个互动微课原型，今天观察的是产品是否清楚易用。请按你的理解操作并说出想法，可以随时停止。它目前只在本机保存记录，教师生成使用规则模板。”

**背景问题，2 分钟**

- 最近一次学习软件工程或使用 AI 编程工具时，最难的部分是什么？
- 你通常如何判断自己学会了一个概念？
- 教师补充：平时怎样准备短课和检查学生参与情况？

**任务操作，7–8 分钟**

| 对象 | 任务（不提示点击位置） | 观察重点 |
|---|---|---|
| 学习者 | 找到“把模糊需求变成用户故事”，完成一个场景并解释反馈含义 | 能否找到入口；是否读懂活动与解释 |
| 学习者 | 完成微课并重新打开页面，找到自己的进度 | 是否理解完成状态；是否知道记录保存范围 |
| 教师 | 为一个自己熟悉的主题生成草稿，修改章节正文或思考题，核对配套情境题后发布并查看 | 能否完成闭环；是否误以为接入了真实 AI |
| 教师 | 找到参与记录，并说明这些数据代表哪些人 | 是否理解仅为当前浏览器事件 |

观察者先不指导；用户停滞时记录，再提供必要帮助。不能把“在提示下完成”算成独立成功。

**追问，3–4 分钟**

- 哪一步让你停顿或不确定？请指出具体位置。
- 你认为课程草稿是怎样产生的？使用前会检查什么？
- 反馈是否改变了你对题目的理解？请举一例。
- 下次你会用它完成什么学习或备课任务？缺少什么？
- 按 1–5 分评价任务难易程度，并说明原因。

## 如何把记录转成迭代

将每个问题绑定到一个任务和具体证据，标记影响与出现次数。优先修复阻止完成任务、产生错误理解或丢失数据的问题。第一轮目标是参与的学习者均能独立完成微课，参与的教师能正确识别模板生成和本机数据范围；若未达到，记录原因并改进后复验。这些是验收目标，不是结果，也不是统计性结论。
